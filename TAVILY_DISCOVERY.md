# Tavily product-discovery feasibility test

This is a server-side, local-only experiment. It does not feed the UI, send user preferences to Tavily, write to Supabase, or establish any license to reuse merchant content. `TAVILY_API_KEY` belongs in `.env` or `.env.local`, never `NEXT_PUBLIC_*`. The client uses Tavily's official HTTP Search and Extract endpoints.

## Run

From the project directory, run `node scripts/tavily-discovery.mjs`. It writes `artifacts/tavily-discovery.json` and replaces the previous run's artifact. Its optional settings are `TAVILY_DOMAINS` (comma-separated permitted search domains), `TAVILY_MAX_CREDITS` (default 14, max 50), `TAVILY_MAX_REQUESTS` (default 13, max 30), `TAVILY_MAX_RESULTS` (default 5, max 10 per query), `TAVILY_MAX_EXTRACT_PAGES` (default and max 5), and `TAVILY_MIN_INTERVAL_MS` (default 300). The budget and request limit apply **per process/run**, not across concurrent processes or a user's Tavily account. The script reserves one credit before every basic Search or up-to-five-URL basic Extract call; even a failed or timed-out request counts against its conservative cap. It requests and records Tavily's `usage.credits` separately. Because Tavily bills basic extraction in groups of five successful URLs, reported usage can be zero even if extraction succeeded. Consult Tavily billing for account-level charges and other activity.

The default domain plan performs five searches each for Zalando and Primark and two fallback searches for Adaptawear, in that order. Search candidates are only URLs and titles returned by search and are not product verification. They are domain-checked, require HTTPS and a product-shaped path, are de-duplicated, and are saved with search-query provenance. Tracking parameters are removed; product/variant query parameters remain. There may be false negatives, including uncommon merchant URL formats. Search snippets, full page content and general search-result images are not saved.

## Extraction and safety gate

`lib/product-discovery/source-policies.json` records reviewed source access rules. Extraction is **off by default** for every present retailer. A future source must have extraction for this specific use reviewed against its current terms and robots policy; only then should its record be updated with `extract_for_research: true`, `reviewed_at`, and an HTTPS `terms_url`. The flag is a manually maintained gate, not proof of a license. The script independently fetches `robots.txt` for each candidate immediately before submitting it to Extract, fails closed on unavailable/redirected robots files, and conservatively treats matching wildcard/Tavily disallows as blocking even when an Allow rule could override them. This can reject permitted URLs. Stop if a site denies access; there is no retry via proxy, login, or anti-bot bypass.

`schemas/discovered-product.schema.json` documents the intended local product JSON. `normalizeExtracted` requires a product-shaped URL and a clothing-specific heading and conservatively extracts only simple, explicit, labeled fields or short seller-claim lines. `validateNormalizedProduct` validates its core shape, URL/domain and evidence before returning it. It is not a full JSON Schema validator or a guarantee of accuracy. Extracted facts are labeled `unverified_seller_claim`; content may be stale or refer to a variant. `last_checked_at` records when this tool obtained the extraction, not when the retailer updated it. Price, availability, shipping and delivery remain unknown unless the narrowly supported labeled forms are present. Image URLs are intentionally left empty: neither a search image nor a generic extracted page image establishes product association and permission to display it. No blanket allergy-safe classification is produced. Human review and actual access/reuse rights are required before using any output.

## Run on 2026-11-02

- `artifacts/tavily-discovery.json`: 12 successful domain-restricted Search requests; three Adaptawear product-shaped search candidates; zero accepted Zalando or Primark product URLs; zero Extract calls and zero normalized products. The original Zalando product URL filter was overly strict and was corrected after the run. Raw rejected results were not retained, so the initial run cannot establish how many valid Zalando product URLs it missed. The original run also did not record the number of rejected search results for each query.
- `artifacts/tavily-priority-check.json`: two additional successful searches, one for each priority domain. Those returned Zalando category pages and Primark editorial/corporate pages, rather than product URLs. They are raw search diagnostics and are not normalized or licensed records.
- Tavily reported 12 + 2 = **14 credits** across the 14 successful basic Search requests. The initial run's conservative reservation was 12 and the supplemental check reserved 2. No Extract credits were used. This is per-response usage, not a reconciliation of all account activity.
- Successful product-page extractions: **0**. Valid products, verified product images, valid extracted prices, documented composition and documented product accessibility features: **0**. No live extraction quality or reliability claim is possible.

Direct public robots checks for `www.zalando.de` and `www.primark.com` returned HTTP 403 to the research client. No bypass was attempted. [Primark's UK terms](https://www.primark.com/en-gb/terms-and-conditions) restrict copying, commercial use, and links beyond the homepage without permission. [Adaptawear's terms](https://adaptawear.com/terms-conditions/) reserve site/database rights and limit copying, commercial use, and deep linking without written consent; its robots file was accessible but that does not grant reuse rights. [Livostyle's openly licensed dataset](https://github.com/arturayupov/livostyle-catalog-mcp/blob/main/LICENSE) is a potential future source, but its dataset license does not by itself establish rights to extract the retailer website. Zalando's terms and source-specific reuse permissions need further review. No source here is approved for catalog persistence or publication.

The remote catalog was checked read-only: all nine catalog tables exist with RLS enabled, and anonymous/authenticated clients cannot insert into them. No service-role credential or authorized ingestion permission was verified. No Supabase upsert implementation or write was attempted because there are no permitted, validated products or confirmed source reuse rights. A future ingestion adapter must independently verify permissions, URL and image rights, transactionality, idempotent source identities, evidence scope, freshness, and server-side authorization before any database write.
