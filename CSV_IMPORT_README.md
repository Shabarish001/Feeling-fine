# CSV catalog import

The importer reads both files under `data/imports/` through `scripts/preview-imports.py`, normalizes and conservatively deduplicates direct URLs, and regenerates `artifacts/spreadsheet-import-preview.json`. Product links inferred from URL shape and seller claims are not independently verified. It never treats a shared category link as a product URL.

From the application directory, use `node scripts/import-adaptive-catalog.mjs --dry-run` or `node scripts/import-csv-products.mjs --validate`. Both display every candidate and review reasons without contacting Supabase. `--approved-import` processes only eligible records and requires `node --env-file=.env scripts/import-csv-products.mjs --approved-import`. Do not place the server key in a client environment variable or source control. The dry-run currently reports 28 records, zero eligible.

Reviewers can supply `data/imports/product-approvals.json` keyed by the exact original product URL. The record requires `product_url`, `product_evidence_url`, `url_verified: true`, a recent `checked_at`, and `field_approvals.metadata` with `status: "approved"`, `scope: "public_catalog"` and an HTTPS `reference_url` documenting the legal or contractual basis for the particular factual use. A review may rely on a legally assessed basis and need not assert that copyright applies to individual facts. An unknown basis is not approval. Supabase catalog tables are publicly readable: metadata inserted there is not a private draft.

Fields are independent. An image requires its own `field_approvals.image`, matching `image_url`, and `image_matches_product: true`. A price requires `field_approvals.price`, matching `price` and `currency`, `price_verified: true`, `reference_url`, and a fresh `price_checked_at`. Seller feature claims require `field_approvals.features`, `accessibility_verified: true` and `feature_evidence_url`; they remain labeled seller claims. Materials require `field_approvals.material`, `material_verified: true` and `material_evidence_url`. Every field approval has `status`, `scope` and `reference_url`. Unapproved or unverified optional fields are omitted rather than blocking metadata. Missing category is explicitly recorded as `unknown`. Original descriptions are not imported. An approval is a human assessment, not a programmatically verified license.

Approved metadata maps to products, optional verified variants, retailers and offers. Separately approved fields map to price observations, images with rights references, materials, attributes and seller-claim evidence. Stable product IDs derive from a canonical URL while the original retailer URL, including its product variant, is retained. The product card marks incomplete listings when an approved image, observed price, direct link or accessibility evidence is missing. No approved data exists in the current inputs.

## Transaction deployment blocker

`supabase/import-tools/csv_catalog_import.sql` is a proposed function, not a migration and **not deployed**. Approved import requires this function to be independently reviewed and installed in the target database after appropriate authorization. It checks that the caller is `service_role`, executes each product and its related rows in one transaction, uses deterministic IDs, refuses conflicting existing data and supports safe reruns with identical inputs. It performs no updates or deletions. Changes to previously imported values stop with a conflict and need a separate reviewed synchronization strategy. Its URL lock coordinates this importer only; other writers must share the lock or be controlled. Each product is a separate transaction, so earlier successful products remain if a later product fails. If a request times out or read-back fails, inspect state before rerunning.

The function compiled and its insert, repeat, collision and rollback behavior passed in a disposable PostgreSQL container with simplified fixture tables. That is not a test against the remote schema or an end-to-end Supabase RPC/read-back test. No retailer rows or SQL function were deployed remotely. Run `node --test tests/*.test.mjs` for local validation.

The authorized remote diagnostic inserted a uniquely identified synthetic product, read it, deleted it by exact ID and identifying fields, and verified its absence. It did not touch retailer records.
